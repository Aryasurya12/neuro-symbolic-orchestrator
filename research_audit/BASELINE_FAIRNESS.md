## 1. Executive Summary

This report evaluates the experimental fairness, prompt parity, and architectural symmetry across all four execution modes evaluated in the Neurasym benchmark suite (`study_run_02.csv`, `run_20261009_093328`):

1. **Mode 1 (Raw LLM / Pure Generative)**: Unstructured natural language generation via LLM.
2. **Mode 2 (Schema LLM / Structured Generative)**: Pydantic-guided JSON generation via LLM.
3. **Mode 3 (Pure Symbolic / Rule-Based Solver)**: Regex SCOPE parser mapped to deterministic mathematical solvers (HiGHS MILP, Z3 SMT, PSO).
4. **Mode 4 (Neuro-Symbolic Orchestrator)**: Few-shot neural extractor (`NVIDIAExtractor` / `GroqClient`) mapped to archetype contracts, verified deterministic solvers, and explanation generation.

Our independent investigation identifies **two major structural fairness defects** in the current evaluation pipeline:
1. **Critical Evaluator Bias against Mode 2 (P0 Defect)**: Mode 2's structured outputs are evaluated against a fallback archetype generated by Mode 3's rule-based SCOPE parser. When SCOPE fails on colloquial/Hinglish text, it defaults `requested_problem_type` to `"ILP_VM_Allocation"`. Consequently, Mode 2 queries that correctly identified Disaster Recovery or Continuous Scaling were falsely penalized as `TASK_INCOMPATIBLE` / `WRONG_PLAN`.
2. **Mode 1 Post-Hoc Regex Extraction Bottleneck (P1 Defect)**: Mode 1 is prompted for plain prose, but the grader uses rigid heuristics to extract allocation tuples. When valid answers use colloquial formatting, the normalizer marks `NORMALIZATION_FAILURE` and records blank/null success.

## 3. Verified Evaluator Bias & Baseline Disadvantages

### 3.1 Mode 2: The SCOPE Defaulting Trap (Verified P0 Defect)

#### Mechanism of the Failure
In `run_all_modes_comparative.py` (lines 565–595):
```python
# Mode 2 execution and evaluation pipeline
contract = scope_parser.parse(query_text)
if contract is None:
    # Rule parser failed to detect archetype from text
    requested_problem_type = "ILP_VM_Allocation"  # <-- FORCED DEFAULT!
else:
    requested_problem_type = contract.archetype
```

When Mode 2 executes, it generates a JSON object directly using the neural model. For example, on `Q11_DR_MULTI_REGION_RTO_RPO_ZERO`, Mode 2 generates:
```json
{
  "task_type": "Z3_Graph_Disaster_Recovery",
  "source_region": "us-east-1",
  "target_region": "us-west-2",
  "rto_minutes": 0,
  "rpo_minutes": 0
}
```
However, because the query text was complex, `scope_parser.parse()` failed, setting `requested_problem_type = "ILP_VM_Allocation"`.

When `OutputNormalizer.normalize_mode2_json(json_text, requested_problem_type)` was called:
- It observed `task_type = "Z3_Graph_Disaster_Recovery"` in the JSON.
- It compared it to `requested_problem_type == "ILP_VM_Allocation"`.
- It raised a mismatch and set `explain_label = "TASK_INCOMPATIBLE"` with `normalization_status = "NORMALIZATION_FAILURE"`.

#### Empirical Impact
This defect unfairly penalized Mode 2 across **7 queries** in `study_run_02.csv`:
- `Q11_DR_MULTI_REGION_RTO_RPO_ZERO`
- `Q12_DR_FAILOVER_CROSS_CLOUD_LATENCY_50MS`
- `Q16_SCALING_HPA_CPU_SPIKE_80PCT`
- `Q17_SCALING_SCALE_DOWN_IDLE_BURST`
- `Q18_SCALING_BANDWIDTH_BURST_100_TO_500MBPS`
- `Q21_CONFLICTING_HIGH_VCPU_LOW_BUDGET`
- `Q29_UNSUPPORTED_QUANTUM_ANNEALING_COMPUTE`

Mode 2's published accuracy was suppressed to **34.5% (10/29)**. Graded fairly against the ground-truth manifest archetypes, Mode 2's structured extraction accuracy is significantly higher.

### 3.2 Mode 1: Plain-Text Extraction Asymmetry (Verified P1 Defect)

Mode 1 is asked to generate conversational responses. However:
1. **No In-Prompt Calculator**: Unlike Mode 4, which delegates pricing to mathematical integer linear programming, Mode 1 must perform multi-variable arithmetic in generative tokens.
2. **Post-Hoc Regex Brittleness**: The grader uses regular expressions to look for specific patterns like `3x t3.xlarge` or `Cost: $120.00`. If Mode 1 writes `"We recommend provisioning three t3.xlarge instances totaling 120 USD"`, regex extraction often fails, logging `NORMALIZATION_FAILURE` and recording blank `task_success`.
3. **Refusal Recognition Gap**: When Mode 1 correctly advises the user that a request is impossible or conflicting (e.g., `Q28_UNSUPPORTED_GPU_LLM_TRAINING_CLUSTER`), the natural language refusal was not caught by the normalizer, resulting in blank `task_success` instead of `CORRECT_REFUSAL`.

---

### 3.3 Mode 3: Hand-Crafted Rule Parsing Advantage & Scope Inversion

Mode 3 bypasses neural extraction entirely and relies on hand-crafted regular expressions and keyword templates (`scope_parser.py`).
- **Advantage on Synthetic Benchmarks**: On queries formatted identically to development templates, Mode 3 achieves 100% extraction accuracy with 3.6 ms runtime.
- **Vulnerability to Real-World Variation**: On conversational Hinglish or ambiguous inputs (`Q20`, `Q22`, `Q23`), Mode 3 either fails to parse or strips critical modifiers.
- **Scoring Inversion on Q19**: In `Q19_SCALING_CONFLICTING_CPU_TARGET_CEILING`, Mode 3 stripped the conflicting ceiling, generated an unconstrained valid plan, and was awarded `task_success = 1` by an evaluator fallthrough bug, despite the ground truth demanding `CONFLICTING_REQUIREMENTS`.

## 4. Recommendations for Fair & Defensible Comparative Benchmarking

To ensure scientific defensibility in future runs:
1. **Decouple Mode 2 from Mode 3 Parser**: Always pass the query's ground-truth manifest archetype to `normalize_mode2_json`, never the SCOPE parser runtime fallback.
2. **Standardize Task Refusal Parsing**: Add semantic refusal classifiers for Mode 1 and Mode 2 plain text and JSON outputs so correct refusals receive `CORRECT_REFUSAL` (`task_success = 1`).
3. **Provide Full Catalog in Prompt for Modes 1 & 2**: Ensure token budgets and catalog tables are identical between Mode 1, Mode 2, and Mode 4.
4. **Report Both Extraction Accuracy and Mathematical Feasibility**: Disentangle "Did the model understand the query?" from "Is the allocated solution mathematically optimal?".
